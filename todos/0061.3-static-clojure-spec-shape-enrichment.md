## Context

Some Clojure projects already express named data contracts with
`clojure.spec.alpha`. Consume those declarations only as source-level evidence
on top of #0061.2's schema-free baseline. The helper must never add Spec, load
namespaces, query `s/get-spec`, call a Spec function, or imply a declaration is
runtime-enforced.

Spec uses a separate **constraint overlay** domain. Its `:required` and
`:optional` requirements describe a declaration, never a flowing value's
baseline `:present`/`:maybe`/`:absent` facts. Baseline summaries and flows are
therefore byte-identical whether or not this ticket's records are emitted.

## Static Recognition Contract

- [ ] Recognize a Spec form only when kondo resolves its callee to
      `clojure.spec.alpha`, regardless of the source alias. Record unresolved
      lookalikes as ordinary opaque calls. Resolve `::local-name` with the
      static namespace declared by the file and retain explicitly-qualified
      keyword names unchanged.
- [ ] Index literal-name `s/def` declarations. A dynamic definition name or a
      second definition of the same Spec name produces a
      `:dynamic-spec-name` or `:duplicate-spec-definition` gap and no merged
      semantic shape. References form a directed graph; cyclic references are
      retained as named references and emit one `:cyclic-spec-reference` gap
      instead of being unfolded.
- [ ] Represent every interpretable declaration as a constraint, never as a
      #0061.2 value shape: scalar `{:kind :scalar-constraint :name kw}`;
      map `{:kind :map-constraint :openness :open :requirements {...}}`;
      collection `{:kind :collection-constraint :collection-kind :any|:vector
      :element constraint}`; tuple `{:kind :tuple-constraint :items [...]}`;
      union, conjunction, reference, and predicate-constraint records. A map
      constraint may also carry `:arbitrary-key-constraint` and
      `:arbitrary-value-constraint` for `s/map-of`.
- [ ] Interpret exactly this Spec DSL in v1:

      | Source form | Static constraint/evidence |
      | --- | --- |
      | keyword reference or known core predicate (`string?`, `int?`, `integer?`, `pos-int?`, `uuid?`, `keyword?`, `boolean?`, `vector?`) | reference or scalar/collection-kind constraint |
      | `s/nilable x` | union of `x` and nil when `x` is interpretable |
      | `s/or tag x ...` | sorted union of fully interpretable alternatives |
      | `s/and x ...` | conjunction of one structural child and named predicate constraints; `vector?` plus collection constraint sets collection kind vector |
      | `s/keys` | open map constraint with `:req`, `:opt`, `:req-un`, and `:opt-un`; `-un` strips only the keyword namespace |
      | `s/coll-of` or `s/every` | generic collection constraint with unknown length, never a vector by itself |
      | `s/map-of` | open map constraint with arbitrary key/value constraints |
      | `s/tuple` | positional tuple constraint |
      | `s/cat` | named fixed argument-position constraints only |

      Interpret only fixed arities: `s/nilable` 1; `s/or` and `s/cat` an even
      positive sequence of literal tag/form pairs; `s/and` one or more forms;
      `s/keys` only literal `:req`, `:opt`, `:req-un`, `:opt-un` vectors;
      `s/coll-of`/`s/every` exactly one form (any options, including `:kind`,
      are opaque); `s/map-of` exactly two forms; and `s/tuple` zero or more
      forms. Recognize core predicates only when kondo resolves their fully
      qualified var identities, not by source spelling. No other
      `clojure.spec.alpha` form is interpreted in v1. `s/merge`, `s/alt`,
      regex operators, generators, custom conformers, arbitrary predicates,
      and dynamic construction remain named opaque evidence with a gap.
- [ ] `s/keys` is always open-map evidence. It creates `:required` requirements
      for `:req`/`:req-un`, `:optional` requirements for `:opt`/`:opt-un`, and
      does not prove unrelated keys absent. A referenced key Spec contributes a
      nested constraint only when its definition is unambiguous and
      interpretable.
- [ ] Recognize `s/fdef` only when it has a literal target symbol resolved to
      the current namespace when unqualified (or kept as its explicit qualified
      var), `:args` is an interpretable `s/cat`, and `:ret` is an interpretable
      shape/reference.
      Emit a `:declared-function-contract` record that maps fixed argument
      positions and return shape to that var. It never changes a function
      summary or proves calls are instrumented.
- [ ] Recognize a direct `(s/valid? literal-spec tracked-value)` used as the
      test of `if`, `if-let`, `when`, or `cond`. Always emit a
      `:validation-site` record. The true branch receives a separate
      `:conditional-spec-overlay` reading “assuming the runtime binding for
      this Spec name matches this source declaration”; it never changes a
      baseline summary/flow. Its relation is `:compatible`, `:conflict`, or
      `:unknown`: scalar kinds must match; nilability and unions are compared
      distributively; map requirements compare required/present, required/absent
      (conflict), required/maybe (unknown), and optional (never conflict);
      tuple, generic-collection, and arbitrary-map constraints have relation
      `:unknown` unless a later explicit comparison rule exists; opaque/cyclic
      constraints are unknown. A conflict retains both facts and a gap; it does
      not imply the branch is unreachable. Dynamic specs,
      transformed values, or non-identical paths emit validation evidence plus
      a gap but no overlay. `s/assert`, `s/conform`, `s/explain*`, and
      instrumentation calls are opaque in v1.

## Acceptance Criteria

- [ ] Extend canonical EDN with sorted `:spec-definitions`,
      `:declared-function-contracts`, and `:validation-sites`. Each includes
      name/target identity, source form category, constraint or opaque reason,
      location, provenance `:spec-declaration` or `:spec-validation-site`, and
      gaps; a validation site contains its conditional overlay/relation.
      Baseline summaries/flows remain present and unchanged when these records
      are removed.
- [ ] With Spec analysis disabled versus enabled over the **same source**, the
      baseline `:summaries`, `:flows`, and baseline `:gaps` are byte-identical.
      A separate fixture may remove only top-level declarations that do not
      affect control flow; do not claim identical baseline flow after removing
      an `s/valid?` branch test.
- [ ] Fixtures cover aliases, qualified/unqualified names, each allowed form,
      `:req`/`:req-un`/`:opt`/`:opt-un`, references, duplicate/cyclic/dynamic
      definitions, `s/fdef`, branch-local `s/valid?`, dynamic validation, and
      an opaque custom predicate. All output remains source-only and
      byte-stable.
- [ ] Update `languages/clojure.md` with the exact table above and explain
      declared vs branch-local validation evidence. Update the dataflow skill
      only after #0061.4 defines how these records appear in the graph.

## E2E Spec

GIVEN a fixture with ordinary baseline shape flow plus existing Spec
Declarations, an `s/fdef`, and true/false paths around `s/valid?`
WHEN the helper analyzes its entry var
THEN it emits named declared shapes and branch-local validation evidence without
loading the fixture namespace, while baseline projection is byte-identical with
the Spec pass disabled versus enabled over the same source; a separate removal
fixture removes only top-level declarations that do not change control flow.

## Notes

Spec is optional enrichment only. This task must not introduce a Clojure Spec
dependency to any analyzed project or interpret a Spec declaration as a static
type or a runtime guarantee.
